Kafka backpressure simulator

Two copies of the same consumer receive the same messages. One takes everything into memory. The other asks an admission gate first. Slow the downstream system and watch what each one does.

What this is. A simulation of a Kafka consumer, written from scratch for this portfolio. The gate logic follows the Java library in the repository (AIMD limiter, byte budget, workflow quotas), which has its own JUnit tests. The numbers illustrate behaviour; they are not a benchmark.

Try it: press “Slow down workflow A's downstream”. It makes that system 6 times slower, the kind of incident a third-party API has on a bad day.

Adaptive concurrency limit for workflow A, with backpressure

The limit climbs by one per round of successes and is cut by 30% when the downstream rejects a call, so it hovers at what the downstream can take. The grey line marks 12 concurrent calls, where the downstream starts rejecting.

How the gate works

Byte-based admission

Each message's heap footprint is estimated from its payload size. The gate keeps the total for in-flight messages under a fixed budget, so memory use is bounded whatever the message sizes are.

AIMD concurrency

Additive increase, multiplicative decrease: the same control loop TCP uses. The limit grows slowly while calls succeed and drops sharply on rejections, timeouts or heap pressure.

Workflow isolation

Every workflow has its own limiter and may hold at most 60% of the byte budget. A slow integration fills its own quota and leaves the rest for everyone else.

What is not admitted stays in Kafka. Overload then shows up as consumer lag, which is durable and cheap, instead of as heap growth, which ends in an OutOfMemoryError and a redelivery storm. Model: 512 MB heap, each in-flight message costs 2.5 times its payload size, each downstream handles 8 concurrent calls and rejects beyond 12.
