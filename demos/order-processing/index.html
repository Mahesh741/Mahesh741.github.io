Order processing pipeline

An order is accepted at once and processed asynchronously. When payment fails it is retried with exponential backoff on separate Kafka topics, then dead-lettered, and can be replayed once the outage is over.

What this is. A browser walkthrough of the flow. The backend it mirrors is a Spring Boot, Kafka and PostgreSQL service in the repository, with the same topics, attempt counts and backoff. Its end-to-end tests run against an embedded Kafka broker; this page does not call a server.

Try it: switch the payment gateway to an outage, place an order and watch it move through the retry topics to the dead-letter topic. Then end the outage and press Replay.

What the backend does

Non-blocking retries

A failed order moves to a retry topic and waits there. The main topic keeps flowing, so one bad order never blocks the orders behind it.

Retry only what can be fixed

A payment timeout gets four attempts with 1, 2 and 4 second backoff. An unknown SKU cannot be fixed by waiting, so it is dead-lettered on the first attempt.

Idempotent processing

Kafka delivers at least once. A completed order ignores duplicate events and the payment call is keyed by order id, so a redelivery never charges twice.
